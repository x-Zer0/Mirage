## 一、阻断发布

### B1. 验收没有执行，关键待核验项没有结论

`docs/acceptance/M9.md`～`M12.md` 中所有手工验收项的结果都是“待统一验收”，静态检查是唯一通过的部分。以下几项直接决定功能是否可用或文案是否正确，必须实测：

- M9 #7：TUN 加注入最小 DNS 时，服务再次执行策略后 `ipv6` / `dns.ipv6` 是否仍然保留。这是设计 §1 “服务不需要改动”这一前提的唯一验证。
- M10 #6：Hosts 对经代理节点转发的连接是否生效（设计 §2.1、§9）。
- M11 #9：附加规则是否优先于订阅规则命中。
- M12 #3、#8：普通权限能否实际增删豁免，UAC 回退路径是否正常。

**建议**：先完成统一验收，把结果填回各验收文档，再合并 master。

### B2. 界面文案中仍有“待核验”

- `ui/pages/rules.slint:266`：Hosts 说明写的是“可能不生效（待核验）”
- `ui/pages/settings.slint:168`：IPv6 说明写的是“TUN 下的 IPv6 接管尚待核验”

“待核验”是内部文档用的标记，不应该出现在发布版的界面上。**建议**：根据 B1 的实测结果改成确定的说法。例如经代理不生效时写“仅对直连流量和 TUN 下的 DNS 解析生效”；TUN IPv6 未验证通过时写“TUN 模式下暂不保证 IPv6”。

### B3. mirage-svc 有改动，与设计文档“服务不必升级”的结论矛盾

`caebe61` 修改了 `crates/mirage-svc/src/main.rs`（安装 rustls ring provider）。`service::ready()` 会比较已安装服务和随包服务的哈希，所以老用户升级后服务会被判定为“未就绪”，需要重新安装服务（会弹 UAC），否则无法使用 TUN 热重载的修复。

但设计文档 §1 和 M9 验收文档都写着“mirage-ipc 和 mirage-svc 都不需要改动……服务也不必升级”。

**建议**：

- 修正设计文档 §1 和 M9.md 中的这一结论。
- 在发布说明中写明“升级后需要在设置页重新安装 TUN 辅助服务”，并实测一次“旧版本服务 → 新版本客户端”的升级路径。
- 发布前更新版本号（目前工作区仍是 `0.1.0`）。

## 二、中等问题（建议发布前修复）

### M1. 覆写热重载失败时，`failed_overlay` 可能记录从没尝试过的覆写，导致新保存的规则永远不生效

位置：`app/overlay.rs:113-125`

```rust
if self.user_overlay() == attempted { /* 恢复 ipv6 / unified_delay */ }
let restored = self.user_overlay() == previous;
if !restored {
    self.failed_overlay = Some(self.user_overlay());
}
```

触发场景：

1. 用户修改 IPv6 并保存，热重载开始（`Reloading`）。
2. 重载还没结束，用户在规则页保存了附加规则。`-t` 通过后写入文件，`sync_user_overlay` 因为状态不是 `Running` 而延后执行。
3. 第 1 步的热重载失败。此时 `user_overlay()` 已经包含新规则，不等于 `attempted`，所以 IPv6 设置**没有恢复**；它也不等于 `previous`，于是把**从没尝试过**的新覆写记进 `failed_overlay`。
4. 随后 `finish_overlay_reload → sync_user_overlay` 发现 `wanted == failed_overlay`，直接跳过。

结果：新规则已经存盘，提示也说“已保存，正在热重载内核”，但运行中的内核一直没有用上新规则；IPv6 设置还停留在失败的值，与实际运行状态不一致。

**建议**：

- 只记录真正失败的那份覆写：`self.failed_overlay = Some(attempted.clone())`。
- 恢复设置时不要比较整个覆写，只比较 `ipv6` / `unified_delay` 两个字段是否仍等于 `attempted` 中的值，再决定是否恢复。

### M2. 订阅更新热重载时，覆写导致的失败会把新订阅版本标为无效

位置：`app/reload.rs:126-159`，`runtime::reload`

设计 §1.1 特意让导入和更新校验使用空覆写，目的是“避免用户覆写导致的失败把订阅版本标为无效”。但订阅更新后的热重载（`runtime::reload → apply_revision`）会用当前覆写合成配置，并且**不先执行 `-t`** 就直接 `PUT /configs`。

如果失败是覆写和新版本组合引起的，候选版本会被 `mark_invalid`。如果回滚到 last_good 也失败（同一份覆写），会进入 `NeedsRestart`，重启时的 `-t` 同样会失败，最终断开连接，而且提示里只说“新版本应用失败”。

在大多数情况下，覆写不会导致 `PUT /configs` 失败，因为不存在的目标都会被跳过，所以出现概率不高，但一旦出现就很难排查。

**建议**（任选一种）：

- 失败后用空覆写再试一次候选版本。如果能成功，说明问题在覆写，不标记版本无效，并提示用户去规则页检查。
- 至少在覆写非空时，在失败提示中加上“可能由附加规则或 Hosts 导致”（与 M3 一起实现）。

### M3. 设计 §1.3 末段“错误提示注明可能由附加规则或 Hosts 导致”没有实现

全局搜索没有找到相关文案。切换到其他配置（会重启内核）或启动连接时，如果 `-t` 因为用户覆写失败，用户只会看到内核报错，不会想到去规则页排查。

**建议**：在 `on_started` 的失败分支和 M2 的失败分支中，当 `running/req.user` 中的规则或 Hosts 非空时，追加一句“可能由附加规则或 Hosts 导致，可在‘规则’页停用后重试”。

### M4. 设置页保存后，“有未保存的修改”可能一直显示

位置：`ui/pages/settings.slint:109-131`

工作副本用 `property <string> bypass: root.saved-bypass;` 初始化，用户编辑之后这条绑定就断开了。后端保存时会对输入做规范化：例外列表把换行、逗号统一成 `;`，端口和 UA 会 trim。保存成功后，`saved-bypass` 变成 `a;b`，而工作副本还是用户输入的 `a\nb`，所以 `dirty` 一直为 true，界面持续提示“有未保存的修改”，“放弃修改”也一直可点。

同样，覆写热重载失败时后端把 IPv6 恢复成原值，界面上的工作副本仍然是失败的值。这种情况下显示“未保存”是对的，但用户不容易看懂。

**建议**：保存成功（`saved-*` 变化）后由 Rust 侧主动把工作副本重置为已保存的值。可以参考 `rules_editor::reset` 的做法，或者增加一个 `settings-revision` 属性，变化时在 Slint 中整体重新赋值。

### M5. 一次保存会执行两次 `mihomo -t`

位置：`app/overrides.rs::save_override → commit_override → sync_user_overlay → runtime::reapply`

规则页保存时，`check_overlay` 已经对同一个版本、同一份覆写执行过 `-t`。写入文件后 `sync_user_overlay` 进入 `reapply`，又执行一次 `compose + -t`，接着 `apply_revision` 再合成一次。已连接时一次保存要做两次 `-t`、三次合成。`-t` 需要加载 geodata，通常要 1～3 秒，用户会感觉保存很慢。

**建议**：给 `reapply` 加一个“已校验”参数，或者在 `ReloadRequest` 中带上已校验覆写的摘要，命中时跳过 `-t`。`reapply` 内部也可以复用第一次合成的 `Composed`，不必在 `apply_revision` 中再合成一次。

### M6. 启动刷新账号：开机自启时网络还没就绪，容易误报

位置：`app/accounts/session.rs:113-118`（需求 6，§10）

开机自启时网络常常还没有就绪（Wi-Fi 尚未连接、VPN 还没起来）。现在第一次失败就会弹系统通知“自由猫账号信息刷新失败”，用户每次开机都可能看到一条误报。

另外，`system_notice` 只有一个槽位，多个账号同时失败时后一个会覆盖前一个，只能看到一条通知。

**建议**：

- 遇到网络不可达类错误（`providers::is_unreachable`）时，延迟 30～60 秒自动重试一次，仍然失败再发通知。会话失效（`AuthInvalid`）可以立即通知。
- 多个账号失败时合并成一条通知，例如“2 个账号刷新失败：……”。

## 四、需求与设计层面的意见

1. **覆写层的分层合理**：放在 `policy::apply` 之后，不修改摘要，不动 mirage-ipc。TUN 服务会再执行一次策略，覆写不可能绕过安全策略。导入和更新校验使用空覆写也正确。
2. **“PROXY”约定（L1）** 建议在设计文档 §3.1 中说明与同名订阅组的关系，避免用户困惑。
3. **Hosts 生效范围**：如果实测确认经代理不生效，这个功能对系统代理模式下的大多数代理流量都不起作用。建议在规则页把说明从帮助图标提升为常驻提示文字，避免用户以为“Hosts 坏了”。
4. **附加规则在非规则模式下**：现在只在页面顶部提示，主界面切到全局模式时没有任何提示。如果用户经常切换模式，可以考虑在模式切换的 Toast 中带一句提示。这一条可选。
5. **需求 6 的通知策略**：见 M6。建议在设计 §10 中补充“网络错误先重试一次再通知”的规则。
6. **文档一致性**：
   - 设计 §1 和 M9.md 中“svc 不需要改动”的说法需要修正（B3）。
   - 设计 §1.3 末段的“错误提示”要么实现（M3），要么从文档中删除。
   - 设计 §2.1 和 §9 在完成实测后改为【已验证】，并同步修改界面文案（B2）。

## 五、安全评审小结

| 项 | 结论 |
| --- | --- |
| 覆写能否绕过安全策略 | 不能。只修改白名单中的键，TUN 服务会重新执行 `policy::apply`；用户规则不能新增 rule-providers，也不能修改监听或控制器相关的键 |
| YAML 注入 | 不存在。规则和 Hosts 都通过 `serde_yaml_ng` 序列化写入，不做字符串拼接 |
| 输入上限 | 规则 2000 条 × 1024 字符，Hosts 2000 行 × 1024 字符，错误最多列出 50 条，都已实现 |
| 提权子命令 | `--set-loopback-exempt` 对每个 SID 做 `S-1-15-2-` 前缀和纯数字段校验，再调用 `ConvertStringSidToSidW`；参数不需要转义；子命令不会初始化 UI，也不会拿到单实例锁。提权的是 `current_exe()`，与现有安装服务的做法一致，没有引入新的风险 |
| FFI 内存 | 枚举结果用 `NetworkIsolationFreeAppContainers` 释放，SID 字符串和转换出的 SID 都用 `LocalFree` 释放；L9 待确认 |
| 文件写入 | `rules.yaml` / `hosts.txt` 都是原子写入；文件被手工改坏时启动不应用，并在页面显示错误 |
