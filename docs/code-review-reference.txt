总体结论

架构与设计要求吻合度很高：mirage-ipc 共享策略避免了应用与服务漂移，§9.3 的强制覆盖表逐项落实，§10.4 的"挂起创建→入 Job→恢复"顺序正确，§11.3 的事务顺序（先写日志再改 WinINet）正确，凭据不落元数据、日志脱敏层设计合理。问题集中在三类：

1. 状态机边界：少量异步结果没有纳入 generation/事务模型，导致 UI 与内核实际状态可能不一致。
2. 失败路径的提交顺序：几处"先破坏后写入"，失败时会丢失恢复能力或用户数据。
3. 热路径上的全量比较/重建：日志页和节点列表在 10,000 条规模下会产生明显 UI 开销。

一、高危问题（建议优先修复）

H1. 启动过程中切换配置不会生效，也不会取消启动

app/profile_actions.rs:160

select_profile 只在 self.running 有值时才重启内核。running 在 on_started 里才被赋值，所以 Starting 期间（最长 15 秒）切换配置只保存了选择：旧启动任务继续用旧 Profile，generation 未变，on_started 的校验通过并安装旧配置。界面显示 B 配置，内核跑 A 配置，无任何提示，只有重新连接才恢复。

修复：Starting 时递增 generation 使旧启动作废（旧结果会走 Ok(stale) 分支被停止），再以新配置启动。

H2. 内核异常退出绕过 TUN 状态回退，proxy_before_tun 被永久钉住

app/supervise.rs:59 直接写 self.view.tun_active = false，而正常路径都走 tun.rs:10 的 update_tun_state(false)。

后果：proxy_before_tun 不被清空。重启成功后 update_tun_state(true) 因 proxy_before_tun.is_some() 跳过快照与 tun_disable_system_proxy 的自动关闭；之后再关 TUN，会恢复一个来自崩溃前的陈旧代理偏好。同时 TUN 关闭这条操作日志也不会记录。

修复：改为 self.update_tun_state(false);。

H3. 系统代理已写入但通知失败时，恢复日志被删除

app/sysproxy.rs:72-74 + platform/windows/sysproxy.rs:97-108

write() 依次执行"写值 → SETTINGS_CHANGED → REFRESH"。前两步中任意一步失败（写值已成功）都会返回 Err，enable() 随即删除 recovery/sysproxy.json。此时系统代理已指向本地端口，但恢复记录没了；进程若在此后崩溃，下次启动 restore() 返回 Nothing，机器被留在指向死端口的代理上——正是恢复日志存在的目的。

修复：把写值作为提交点；两个通知调用改为尽力而为（失败仅记日志）。或返回"部分成功"错误并保留 Applied 日志。

H4. 凭据覆盖先删除旧值再写新值

platform/windows/secret.rs:35-37

短值路径先 remove_file(key) 再 cred_write。CredWriteW 失败（配额、凭据库损坏）时旧订阅 URL / 会话已删除、新值未写入，用户的账号和订阅地址静默丢失。

修复：先 cred_write 成功，再删除旧 DPAPI 文件；外部文件路径失败时回收刚写的文件。

H5. 日志页"暂停滚动"会被模型刷新立即撤销

ui/pages/logs.slint:81 + ui_bridge/models.rs:50-60,406-417

paused 由 ListView.content-y 推导，而 apply_logs 在连接批次到达时整体 set_connection_logs 重建模型。模型替换后滚动位置回到 0，content-y 变化把 paused 改回 false。用户点暂停后几秒内就会被新连接撤销；向上滚动同样会被拉回顶部。

修复：paused 只由按钮写入；滚动只用于"未暂停时感知用户上滚"，且不要回写同一属性。后端 refresh_logs 在暂停时应按 anchor 截断或跳过重建。

H6. YAML 别名放大（订阅内容不可信）

subscriptions/detect.rs:80、providers/ziyoumao/legacy_import.rs:52-65、providers/ziyoumao/subscription.rs:41

serde_yaml_ng 的别名实现会重新展开锚定子树，只受"跳转次数 ≤ 事件数×100"约束。16 MiB 上限发生在展开之前，嵌套别名可以在一秒内产生数十倍于原文的 Value 节点，阻塞或 OOM actor 运行时。三条路径（通用识别、原客户端导入、账号订阅解密后校验）都受影响。

修复：解析前做廉价文本门控（限制别名定义数/引用数），或改用支持节点数上限的解析方式；三条路径共用同一函数。

H7. 热路径上的全量深比较与整组重建

- app/actor.rs:170-185：publish() 在主循环每轮都执行 **current == self.view，日志页打开时每 5 秒的代理轮询要对最多 10,000 条记录做全量 PartialEq。
- ui_bridge/models.rs:50-60：apply 里 p.logs != s.logs、p.groups != s.groups 同样是深比较，发生在 UI 线程。
- ui_bridge/models.rs:206-228：update_groups 的"按行更新"传入的是新建的 GroupRow，其 nodes 是全新的 VecModel；任意一个节点延迟变化都会重建整组（最多 1000 行）。

修复：LogsPage/分组加单调 revision 字段，比较改为比较 revision；publish 用显式脏标记；分组持有稳定的 Rc<VecModel<NodeRow>>，只对变化行 set_row_data。

六、需要你确认的问题

1. 别名限制的边界：订阅中合法的锚点/别名很常见（合并键、节点模板）。你希望是"限制别名引用总数"还是"彻底改用节点数上限"？这决定 H6 的实现方式。
2. 启动时到期配置同时更新：冷启动时若有 10 个配置都过期，是希望全部并发（当前部分并发）还是排队逐个更新？影响 M10 的修复形态。
3. 崩溃重启后的 TUN 语义：内核崩溃后自动重启成功，是否应重新应用 tun_disable_system_proxy（即视为一次新的 TUN 会话）？设计未写明，H2 的修复依赖这个答案。
4. 配置日志按日分文件的时区：当前用 UTC 命名文件、UI 用本地时间分组，UTC+8 的凌晨记录会落到前一天的文件。你希望统一成本地时区吗？
5. 服务连接模型：mirage-svc 同一时刻只接受一个 owner 连接，第二个连接会排队等待。是否需要支持并发（例如诊断与主会话同时查询状态）？
