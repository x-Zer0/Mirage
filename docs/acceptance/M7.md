# M7：TUN 辅助服务与应用集成

日期：2026-10-17  
环境：Windows x86_64、Rust 1.95.0、官方 Mihomo Meta v1.19.32（with_gvisor）。

## 1. 结论与范围

基于 M6 及原有未提交的 `ipc/`、`service/` 草稿，补齐 M7 的共享配置策略、服务生命周期、应用启动器、开关、恢复及设置入口。基础验证使用独立目录 `target/m7-acceptance/`，没有新增单元测试。

**代码与基础验证完成不等于 TUN 实机验收完成。** 本次没有安装 SYSTEM 服务或创建 TUN 网卡；非浏览器流量接管、路由恢复、强制结束 UI/服务后的恢复、不同 Windows 用户的管道拒绝仍需管理员环境实测。不能据此宣称已支持 UDP、IPv6、DNS 劫持的全部组合。

## 6. 使用与限制

```powershell
cargo build --workspace --release -j 1
```

主程序与 `mirage-svc.exe` 放在同一目录。开发环境核心可来自 `assets/core/`；分发时提供 `<exe目录>/core/`，包含 mihomo.exe、GEOIP.metadb、GEOSITE.dat、GEOIP.dat、ASN.mmdb。第一次开启 TUN 会提示安装，安装 / 更新 / 卸载请求 UAC；UI 本身保持普通权限。

服务工作目录为 `%ProgramData%\Mirage\tun-home`，核心日志位于其 `logs/`；服务日志位于 `%ProgramData%\Mirage\logs`。服务只执行 SHA256 匹配的官方核心。暂未签名，Authenticode 校验按设计留待签名发布后启用。

TUN 使用本次会话选择，下次启动仍默认关闭。切换 TUN 会重启核心，已有连接可能中断。stack 与 DNS 的语法已验证，实网稳定性仍待上表验收。M8 的安装包、签名及分发许可证工作不属于本次实现。

## 7. TUN 身份校验故障修复（2026-10-17）

本机日志显示：自由猫冲突提示之后，连接失败发生在 `mihomo.service` 的服务身份校验；SCM 显示 MirageSvc 仍为 Running，但普通用户无法读取该 SYSTEM 进程的映像路径。旧代码把读取失败误报为内核已退出。启动前写入的 `recovery/tun.json` 因同样的校验失败无法清理，随后普通连接和应用重启均被恢复流程阻塞。

客户端现在通过 `GetNamedPipeServerProcessId` 取得管道服务端 PID，再用 `QueryServiceStatusEx` 核对已注册 MirageSvc 的运行状态、独立进程类型及非零 PID。服务注册由 SCM 管理，安装用户仅持启动和查询权限；不再要求普通 UI 打开 SYSTEM 进程，也不接受未经核对的管道端点。旧恢复记录继续由认证后的服务清理，确认成功才删除。

服务通信和身份校验失败单独归类为 TUN 辅助服务不可用，连接状态保留具体原因；热重载遇到此类传输错误仍终止损坏的会话。此次未修改协议和服务端，原安装路径下替换主程序即可使用现有服务。

静态检查：`cargo fmt --all -- --check`、`cargo check --workspace -j 1`、`cargo clippy --workspace --all-targets -j 1 -- -D warnings` 及 `git diff --check` 均通过。未新增或运行单元测试，未进行实际 TUN 连接和路由切换验证。

本次 Release 构建：cargo build --workspace --release -j 1 通过，新程序位于 target/release/Mirage.exe。

## 8. 管道断线后持续报 233 的补充修复（2026-10-17）

第 7 节只修复了客户端验证 SYSTEM 服务的权限问题，未解决服务端的断线状态残留；本次必须同时更新主程序和已经安装的辅助服务。日志显示新版客户端身份已经通过，服务随后立即结束会话，并非路径不匹配或旧客户端未替换。

服务此前对同一个 Tokio NamedPipeServer 循环 disconnect/connect；底层 Mio 仍可能保存上次断线的异步读取结果或错误，下一次握手会读到旧连接的 EOF / 管道错误。现改为每次会话结束后创建新实例，再释放旧实例；期间保留管道名称占用，避免名称被抢占，依然串行管理唯一内核所有者。日志增加握手/收发阶段及实际错误，格式错误不输出 JSON 内容。

客户端将 tun.json 的写入推迟到身份校验和 Hello 成功之后、StartCore 发送之前，避免仅握手失败就新增恢复记录。既有恢复记录仍需服务确认清理，不能直接丢弃。

新增运维入口 Mirage.exe --check-service：通过正式客户端连续执行三次认证、Hello、Status、断开；无需启动内核或修改系统代理。诊断前要求退出正在运行的 UI。该入口用于本机服务排障，没有新增单元测试。

本机更新还发现安装器用 0x0100 代替 SERVICE_STOP，导致 ControlService 因句柄权限不足无法停止旧服务。现改用 Windows API 的 SERVICE_STOP 常量，安装更新已实际成功。

本机验证结果（2026-10-17 15:51，Asia/Hong_Kong）：

- 更新前：正式新版客户端 --check-service 第一次握手稳定返回 os error 233，退出码 1。
- 更新后：已安装 helper 的 SHA256 与 target/release/mirage-svc.exe 一致；连续三次 Hello + Status 成功，退出码 0。
- 非 Mirage 进程连接被拒绝之后：正式客户端再连续三次 Hello + Status 成功，退出码 0。
- 正常启动新 Mirage：自动清理旧 TUN 恢复记录，recovery/tun.json 已不存在；主程序仍运行并完成官方内核文件校验。
- cargo fmt --all -- --check、workspace Clippy（含所有 targets、警告视为错误）通过；安装器权限修改后又单独通过 service Clippy；最终 workspace Release 构建通过。

此次执行的是本机服务运维诊断和实际更新，没有新增或运行单元测试。尚未实际开启 TUN 或验证代理联网，不能把握手和恢复通过描述为完整流量接管验收。
